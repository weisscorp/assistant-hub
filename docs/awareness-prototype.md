# Прототип событий и маршрутизации мобильного ассистента

Основной клиент — существующий Android-ассистент из соседнего репозитория
`android-assistant`. Его текст и локально распознанный голос идут через
`HermesConversation.ask` → `POST /conversation`; входящие сообщения поступают
через существующие `/link/{device}/events` → `HomeInbox`. Новый APK для серверного
демо не нужен. Мобильный запрос теперь также передаёт `phoneDevice`, чтобы
идентичность клиента не менялась при начале нового голосового сеанса.

## Владельцы контекста

Hub — шлюз сообщений. Если включён `context_router`, мобильные реплики обходят
общий Coordinator, его историю, память и поиск по глобальным знаниям. В Hub
сохраняются только выбранный маршрут, время, ID запроса, хеш и состояние передачи.
Текст реплики и ответ в таблицы маршрутизатора не записываются.

Каждая настроенная область имеет отдельного владельца и ссылки:
`product_id`, `feature_id` в RCP, `thread_id` агента или идентификатор исходного
канала/чата. Владелец загружает свой контекст и хранит историю на своей стороне.
Hub передаёт ему текущую реплику, ссылки, отдельный session и каталог возможностей
телефона. Четыре предыдущие пары диалога, присланные телефоном, не пересылаются:
они могут принадлежать разным областям. Ответ владельца в прототипе только текст;
удалённое выполнение телефонных инструментов этим маршрутом не реализовано.

RCP уже предоставляет `get_project_context(product_id)` и `resume(feature_id)`.
Их вызывает агент-владелец через своё подключение к RCP; прототип передаёт ссылки,
но не копирует базу RCP и не загружает глобальный `get_state`. Автоматическое
создание фич, запись решений в RCP и подключение живого RCP здесь не реализованы.
Контракт: https://github.com/deadnodes/ai-development-workspace/blob/main/docs/CONTRACT.md

Выбор области в прототипе идёт по настроенным псевдонимам с границами слов.
«По работе…» и следующая реплика «В проекте…» выбирают разные маршруты.
Только явное продолжение («продолжай», «подробнее», «что дальше», «да», «нет»)
наследует последний успешный маршрут того же клиента и сеанса в течение 30 минут.
Неоднозначный или новый немаркированный вопрос получает уточнение, без отправки
агенту. Это консервативный прототип, а не семантическая классификация нейросетью.

## Запуск демо

Из корня `assistant-hub`:

```sh
python3 tools/awareness_demo.py
```

Открыть URL из stdout: он содержит одноразовый билет входа, действующий 60 секунд.
Сервер слушает только `127.0.0.1`, порт выбирается автоматически. Данные синтетические,
состояние временное. Есть отдельные процессы владельцев `demo-work`/`demo-project`,
каждый со своей базой вне каталога Hub. Они показывают реальный выбор маршрута и
счётчик истории, но не вызывают модель. `Ctrl+C` завершает демо и удаляет состояние.
Никакие рабочие службы, аккаунты, микрофоны или физические телефоны не используются.
«Телефон» демо — синтетическая запись в локальной базе inbox.

В диагностическом пульте проверить:

1. «Что на работе?» → владелец work, первое сообщение.
2. «Что в проекте?» → владелец project, первое сообщение.
3. «Продолжай» → владелец project, второе сообщение.
4. «Как дела?» → уточнение области, без передачи владельцу.
5. «Сводка событий» → те же карточки через мобильный wire-протокол.

В существующем Hub пульт доступен по `/awareness`, с обычной авторизацией владельца.
Демо-события доступны только с `awareness_demo: true`; по умолчанию выключены.

## Подключение владельца

В приватной конфигурации существующего Hub:

```json
{
  "context_router": {
    "routes": [{
      "id": "work-release",
      "label": "Работа / релиз",
      "aliases": ["по работе", "на работе", "рабочий релиз"],
      "owner": "work-agent",
      "context_refs": {"product_id": "PRODUCT_ID", "feature_id": "FEATURE_ID", "thread_id": "AGENT_THREAD_ID"},
      "argv": ["/absolute/path/to/context-owner-adapter"]
    }]
  }
}
```

`argv` — адаптер вашего агента, его нужно предоставить отдельно. Он вызывается
без shell, принимает один JSON через stdin (`version,id,session,route,owner,
context_refs,text,history:[],capabilities`), возвращает JSON `{id,reply}` с тем же ID
и ответом до 1500 символов. Таймаут 22 секунды. Выбор маршрута не выдаёт прав:
адаптер агента самостоятельно применяет свои ограничения и подтверждения.
`tools/awareness_demo.py --owner-state DIRECTORY` реализует этот контракт для демо.

Повтор того же request ID не запускает владельца дважды. При таймауте, ошибке или
перезапуске результат считается unknown. Автоматического повтора нет: внешняя
сторона могла уже принять сообщение. Для долгих задач нужен собственный durable
inbox/протокол статуса агента; в этом прототипе асинхронный ответ владельца не готов.

## События и очередь решений

`POST /api/awareness/events` принимает нормализованный объект:

```json
{
  "source": "slack",
  "external_id": "workspace:channel:message-ts",
  "project": "Работа",
  "correlation": "release-42",
  "title": "Нужен ответ по релизу",
  "body": "Команда спрашивает, выпускаем ли сегодня.",
  "url": "https://example.test/source",
  "needs_decision": true,
  "priority": "important"
}
```

Источники: `slack`, `telegram`, `codex`. Это API адаптеров, а не прямой Slack webhook
или Telegram Bot API: проверку подписей, OAuth, доступ к пользовательским чатам,
постоянное чтение и возобновление курсора должен реализовать отдельный коннектор.
Подключённых живых коннекторов в демо нет. «Последнее событие» не означает,
что сервис подключён или все его сообщения доступны.

Повторы определяются по producer + source + external_id; конфликт содержимого
отклоняется. Объединение каналов только по явному correlation внутри одного project.
Без correlation сообщения независимы. Внешний текст не исполняется. Приоритет и
необходимость решения — явные метки источника, не заключение нейросети.

Очередь событий — ограниченный операционный журнал для доставки и решений,
не каноническая память работы/проекта: максимум 10 000 событий, до 120 новых событий
в минуту на ключ. Автоматическое удаление/retention и промышленная пагинация пока
не реализованы; пульт показывает последние 100 ситуаций. Не включать массовую
загрузку всех рабочих переписок в этот прототип.

`POST /api/awareness/decision` принимает `{id,revision,action}`. Действия:
`take`, `snooze` (seconds 60..604800, по умолчанию час), `close`, `reopen`.
Версия защищает от решения по устаревшей карточке. Отложенная карточка появляется
после срока при следующем обновлении, без фонового звукового напоминания.
Новый event открывает закрытую ситуацию; активное откладывание сохраняется.

`POST /api/awareness/publish` принимает `{id,revision,device}`: только уже
сопряжённое устройство. Доставка идемпотентная, через обычный inbox, без запуска
приложения, ADB, звука или новых команд телефона. `queued_on_phone` значит очередь,
не доказательство прочтения. При сбое повтор той же версии безопасен.
В Android можно спросить «мои события», «сводка событий», «что требует внимания».
Решения пока принимаются через API/пульт: голосовое закрытие, ответ на конкретную
карточку и отправка решения владельцу задачи — следующий этап.

Для приёма событий годится существующий ключ scope `webhook`. Он не может читать
карточки, принимать решения, вызывать владельца через `/conversation` или выбирать
телефон для доставки. Пульт и остальные операции требуют owner.

Проверка: `python3 -m unittest discover -s backend -p 'test_hub_awareness.py' -v`.
Тесты используют временные SQLite-базы, реальные локальные HTTP и отдельные
процессы владельцев; рабочие аккаунты и устройства не подключаются.

## Источник AO для обзора задач

Mini gateway предоставляет Hermes [read-only обзор AO](ao-overview.md): все
проекты и сессии, ссылки, время наблюдения, отдельные статусы задачи и
доступности источника. Тишина не доказывает зависание, кеш явно исторический.
Это чтение не добавляет RCP-коннектор, сохранение разбора или новую отправку поручений.
