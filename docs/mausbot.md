# Кодинговые задачи через OpenMausBot

В режиме **Авто** хаб выбирает между обычным помощником и отдельным кодинговым
ботом OpenMausBot. Классификатор учитывает текущую реплику и историю темы:
«исправь функцию» направляется в кодинг, «что такое рекурсия?» остаётся обычному
помощнику. Продолжение кодинговой работы использует тот же внешний чат.
Выбор агента можно также сделать вручную в интерфейсе.

Это независимая интеграция с [OpenMausBot — Milind Soni и участники](https://github.com/milind-soni/OpenMausBot).
Проверенный контракт: npm `openmausbot@0.1.107`, upstream commit
`8b53c0323dba2099a953ee2d77ab9330cd5acaa7`. Сервер, его агенты и учётные записи
устанавливаются отдельно; исходники и бинарники OpenMausBot в хаб не включены.

## Подключение существующего бота

В OpenMausBot создайте отдельного бота для разработки с нужным рабочим каталогом
и доступным coding CLI. Сохраните точный `bot_id`. Права инструментов, доступ к
файлам и подтверждения настраиваются в самом OpenMausBot. Хаб их не расширяет.

```sh
python3 tools/local_stack.py setup \
  --mausbot-url http://127.0.0.1:18799 \
  --mausbot-bot BOT_ID \
  --route-coding
```

Для удалённого сервера нужен HTTPS и приватный файл токена владельца:
добавьте `--mausbot-token-file /absolute/private/token`. Файл должен принадлежать
пользователю и иметь права `0600`. Проверяется плоский ответ `/api/auth/session`
с `kind=session` и областью `admin`. Права сессии не заменяют разрешения задач.
Локальный headless-сервер в режиме loopback может работать без токена. Не
открывайте этот порт на внешнем интерфейсе.

Состав провайдеров сохраняется в приватном `config.json`:

```json
{
  "providers": {
    "ollama": {
      "type": "ollama",
      "url": "http://127.0.0.1:11534",
      "model": "qwen3:4b-instruct-2507-q4_K_M"
    },
    "mausbot": {
      "type": "mausbot",
      "url": "http://127.0.0.1:18799",
      "bot_id": "replace-with-coding-bot-id",
      "approval_mode": "ask"
    },
    "auto": {
      "type": "routing",
      "general": "ollama",
      "coding": "mausbot",
      "classifier": "ollama"
    }
  }
}
```

Сохраните остальные поля и провайдеры своего файла. Затем перезапустите хаб.
Локальная Ollama должна содержать выбранную instruct-модель. Классификация
возвращает JSON по схеме и не получает инструментов. При ошибке классификатора
или недоступности кодингового агента запрос получает явную ошибку; автоматического
переноса кодинга на другой исполнитель нет.

## Отдельный сервер на компьютере

Для нового изолированного сервера нужен Node.js 24+:

```sh
umask 077
mkdir -p "$HOME/.local/share/assistant-stack/runtime/mausbot"
npm install --prefix "$HOME/.local/share/assistant-stack/runtime/mausbot" \
  --no-audit --no-fund openmausbot@0.1.107
node "$HOME/.local/share/assistant-stack/runtime/mausbot/node_modules/openmausbot/dist-server/openmausbot.js" \
  serve --local --no-pair --no-open --port 18799 \
  --data-dir "$HOME/.local/share/assistant-stack/mausbot"
```

Откройте `http://127.0.0.1:18799`, настройте отдельного бота и подключите его
командой выше. Для автоматического запуска вместе с хабом можно добавить в
приватный конфиг абсолютные пути установленного runtime:

```json
{
  "mausbot_runtime": {
    "node": "/absolute/path/to/node",
    "cli": "/absolute/private/runtime/mausbot/node_modules/openmausbot/dist-server/openmausbot.js",
    "port": 18799,
    "data_dir": "/absolute/private/mausbot"
  },
  "managed_ollama": {
    "binary": "/absolute/path/to/ollama",
    "port": 11534,
    "models": "/absolute/private/models/ollama"
  }
}
```

Оба раздела необязательны. Удалите `managed_ollama`, если используете существующий
сервис Ollama. Эти параметры не скачивают зависимости и модели. Для отдельного
хранилища сначала запустите Ollama с `OLLAMA_HOST=127.0.0.1:11534` и
`OLLAMA_MODELS=/absolute/private/models/ollama`, затем выполните с тем же
`OLLAMA_HOST` команду `ollama pull MODEL`.

`local_stack.py start` запускает настроенные зависимости перед хабом, `stop`
останавливает только свои процессы. Занятый порт без подходящей записи владения
считается конфликтом. Настройки не создают планировщик и не включают запуск при
входе в систему.

## Передача и подтверждение результата

Каждая тема хаба получает отдельную задачу/чат выбранного бота. Новые сообщения
передаются через guarded API с UUID запроса, ожидаемой веткой и режимом разрешений
`ask`. Внешний чат содержит прежние coding-ответы; дополнительно передаются
новые реплики темы, выбранная память и каталог узлов как данные контекста.
OpenMausBot сам управляет доступными ему исполнителями и делегированием.

HTTP `202` означает только приём запроса. Хаб показывает готовый ответ лишь при
`phase=settled` и успешном терминальном сообщении, привязанном к исходному
`requestMessageId`. Чужой или старый ответ, ошибка и отмена не считаются успехом.

Если требуется разрешение, доступ к сервису или секрет, хаб показывает
«Нужен ответ в MausBot». Ответьте в интерфейсе OpenMausBot. Хаб продолжает читать
статус и вернёт подтверждённый итог, в том числе после своего перезапуска.
Разрешение через текст сообщения в хабе не выдаётся. Если новая команда пришла
во время такого ожидания, хаб сообщает, что она не была отправлена; повторите её
после завершения предыдущего запроса.

Кнопка «Остановить» прекращает ожидание и запрашивает остановку только конкретного
запуска по актуальной execution lease. Подтверждение остановки основного бота
не гарантирует остановку всех делегатов; их состояние проверяйте в OpenMausBot.

При обрыве связи или неоднозначном ответе результат отмечается как неизвестный.
Хаб не повторяет POST автоматически и не создаёт второй чат после
неподтверждённого создания. Следующая реплика сначала сверяет предыдущий запрос;
при подтверждённом завершении его итог сохраняется. Неизвестный исход требует
проверки внешнего чата. В режиме `ask` хаб никогда не переключает задачу на
полный доступ. `full` допустим только как отдельная сознательная настройка
владельца и при поддержке upstream guarded API.

## Проверка и ограничения

```sh
python3 -m unittest discover -s backend -p 'test_hub_mausbot.py' -q
python3 -m unittest discover -s backend -p 'test_hub_routing.py' -q
python3 -m unittest discover -s tools -p 'test_local_stack*.py' -q
python3 tools/verify_routing.py --url http://127.0.0.1:11534 \
  --model qwen3:4b-instruct-2507-q4_K_M
```

Протокольные тесты используют синтетический сервер и временную SQLite, без
физических устройств, реальных переписок и запуска внешнего coding CLI.
Они проверяют корреляцию, повторы, разрешения, отмену, восстановление и изоляцию
тем. Их результаты не измеряют точность классификатора; качество маршрутизации
нужно отдельно проверять на установленной модели и репликах вашего приложения.

Проверка 12 октября 2026: 307 backend-тестов и 11 тестов launcher прошли.
Отдельная живая проверка локального классификатора дала 20/20 ожидаемых маршрутов
на небольшой синтетической выборке; это не оценка качества на всех пользовательских
запросах. Сквозной диалог с настоящим OpenMausBot/Codex вернул функцию `add`,
её продолжение с аннотациями типов в том же внешнем чате и ответ Ollama после
смены темы. Использовалась временная база хаба и синтетическая история.
Карточки разрешений и восстановление проверены протокольными fixtures.
При живом запуске из большого каталога upstream checkpoint заметно увеличивал
задержку; для бота стоит выбрать конкретный репозиторий или небольшой workspace.

Долгое ожидание ограничено параметром `timeout` (по умолчанию 900 секунд).
После истечения задача может продолжать работу во внешнем приложении.
Текст карточек и журнал инструментов пока не отображаются целиком в хабе;
для них используется интерфейс OpenMausBot. Совместимость проверяется по
capabilities, но обновление upstream требует повторной проверки контракта.
